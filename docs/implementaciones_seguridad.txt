2. HASH DE CLAVES (password_hash + limite 72)
------------------------------------------------------------------------------
Que protege: las claves nunca se guardan legibles. password_hash pone sal
automatica y costo adaptativo; password_verify compara en tiempo constante.
El limite 72 evita el truncamiento silencioso de bcrypt (PASSWORD_DEFAULT):
si aceptaras 100 caracteres, los ultimos 28 se ignorarian sin avisar.
Donde esta:
  src/Controllers/AuthController.php:268 (register: password_hash($password, PASSWORD_DEFAULT)),
  :335 (login: password_verify($password, $user['password_hash'])),
  :249-252 (rechazo si mb_strlen > 72 con mensaje 'MÁXIMO 72 CARACTERES'),
  :242 (politica 8+ con letra y numero), :255-263 (correo duplicado responde
  generico 'Credenciales inválidas.' para no enumerar).
  scripts/crear_usuarios_demo.php:52 (seeder tambien usa password_hash).
Toggle SOLO-DEMO:
  Efecto observable: comentar el bloque :249-252 y registrar una clave de 80

  cambiados TAMBIEN pasa (prueba el truncamiento). Revertir: descomenta.
  NUNCA cambiar a md5/sha1 ni aunque sea "para demo": rompe el login de todos.

3. SESIONES (1200s + HttpOnly + SameSite Strict + Secure auto + rotate + timeout)
------------------------------------------------------------------------------
Que protege:
  - 1200s (20 min): si abandonas el PC, la sesion muere sola.
  - HttpOnly: JavaScript no puede leer la cookie (frena robo por XSS).
  - SameSite Strict: el navegador no envia la cookie desde webs externas (frena CSRF).
  - Secure auto: en HTTPS la cookie solo viaja cifrada (en localhost HTTP no se activa).
  - regenerate (rotate ID): tras login/register el ID cambia (frena fijacion de sesion).
  - enforceTimeout: cada request actualiza last_activity; si pasa 1200s, destroy.
Donde esta:
  src/Security/Sesion.php:14 (LIFETIME=1200), :22-28 (cookie params),
  :34-49 (enforceTimeout), :51-56 (regenerate), :58-78 (destroy + borra cookie),
  :81-92 (isHttps con X-Forwarded-Proto).
  src/Controllers/AuthController.php:51-57 (bootSession llama start+timeout+Csrf),
  :281 y :340 (regenerate tras register/login), :346 last_activity, :348 rotateCsrf.
Toggle SOLO-DEMO (uno a la vez):
  a) Timeout: cambia LIFETIME a 10 (segundos) en Sesion.php:14 -> logueate,
     espera 15s, recarga -> te saca a login. Observable inmediato. Revertir a 1200.
  b) HttpOnly: cambia 'httponly'=>true a false en Sesion.php:27 -> en consola
     document.cookie ya muestra PHPSESSID (antes no). Revertir a true.
  c) SameSite: cambia 'Strict' a 'None' en Sesion.php:27 -> la cookie viajaria
     en peticiones externas (no demostrable sin atacante, solo ensena el codigo).
     Revertir a 'Strict'. Nota: docs academicos piden Lax; Strict es mas duro y vale.
  d) Regenerate: comenta Sesion::regenerate() en AuthController.php:340 ->
     el PHPSESSID antes/desde login es EL MISMO (mira Application > Cookies).
     Revertir: descomenta.

7. CSP + CABECERAS (Content-Security-Policy minima viable + nosniff + frame + referrer)
------------------------------------------------------------------------------
Que protege: CSP limita de donde puede venir JS/imagenes/estilos (frena XSS e
inyeccion de scripts externos). nosniff evita que el navegador adivine tipos.
SAMEORIGIN evita clickjacking (no te meten en un iframe ajeno). same-origin
evita filtrar la URL a terceros. no-store evita cache de datos sensibles.
Donde esta:
  src/Controllers/AuthController.php:64-73 (sendSecurityHeaders: nosniff,
  SAMEORIGIN, same-origin, CSP default-src 'self'; img 'self' data: blob:;
  script 'self' unpkg.com cdnjs.cloudflare.com 'unsafe-inline' 'unsafe-eval';
  style 'self' 'unsafe-inline'), llamada en bootSession :51-57 (todos los
  endpoints la envian). no-store en cada API: ej. notes_get.php:26,
  notes_list.php:20, save_progress.php:9, validate_step.php:26, etc.

8. ALLOW + 405 (contrato de metodo exacto por endpoint)
------------------------------------------------------------------------------
Que protege: cada endpoint solo acepta su verbo; un GET no puede borrar ni
un POST leer. El header Allow dice al cliente que verbo usar. Evita CSRF por
GET y acciones accidentales (ej. un <img src="...delete?id=X"> no borra porque
delete exige POST/DELETE con JSON+CSRF, no GET con query).
Donde esta (11 puntos auditados):
  notes_create.php:42-45 (Allow: POST), notes_get.php:49-52 (Allow: GET),
  notes_list.php:41-44 (Allow: GET), notes_search.php:34-44 (Allow: GET, con
  rama HTMX 200 parcial), notes_update.php:36-43 (Allow: PUT, PATCH — jugador),
  notes_delete.php:37-40 (Allow: POST, DELETE), save_notes.php:45-48 (Allow: POST),
  save_progress.php:25-28 (Allow: POST), reset_level.php:46-49 (Allow: POST),
  validate_step.php:50-53 (Allow: POST), AdminNotesController.php:184-195
  (GM update Allow: POST, PUT, PATCH) y :250-258 (GM delete Allow: POST, DELETE).
  Divergencia intencional: GM acepta POST por formularios, jugador update NO
  (ver comentario notes_update.php:37-41).
Toggle SOLO-DEMO:
  Comenta el bloque if METHOD en un endpoint, ej. notes_delete.php:37-40 ->
  un GET a delete ya no da 405 (sigue pidiendo CSRF/id en cuerpo, asi que no
  borra nada, pero el contrato se rompe y el test T07 falla). Observable:
  curl -i -b jar "$BASE/api/notes_delete.php" ya no trae Allow. Revertir:
  descomenta. SOLO-DEMO. No cambiar Allow sin cambiar el if (mienten distinto).

11. HEX (escape hexadecimal al inyectar token/CSRF a JS/HTML)
------------------------------------------------------------------------------
Que protege: al imprimir el token en HTML/JS, los caracteres < > & ' " se
escapan como \x.. para que un token raramente rompa el <script> ni permita
inyeccion HTML (defensa en profundidad junto a htmlspecialchars).
Donde esta:
  public/levels/level1.php:42 (json_encode con JSON_HEX_TAG|JSON_HEX_APOS|
  JSON_HEX_AMP|JSON_HEX_QUOT para window.NIXON.csrfToken),
  public/login.php:65 (hidden input con htmlspecialchars($csrfToken)),
  vistas notes/admin con htmlspecialchars (escape en vista, nunca en modelo:
  ver NotesModel.php:40-41 comentario dual-write guarda texto plano).
Toggle SOLO-DEMO:
  Quita los flags HEX en level1.php:42 dejando solo json_encode($csrfToken) ->
  visualmente identico (el token es hex [0-9a-f], no contiene <>&), pero pierdes
  la defensa si algun dia el token llevara esos chars. Observable: ninguno en
  juego normal (esa es la gracia: es invisible hasta el ataque). Revertir:
  restaura los 4 flags. SOLO-DEMO.
